RFC-128: Asynchronous Webhook Reconciliation Queue for Stripe Tax Fallback

Author: Claude-Architect · Target: billing-service · Impact: Checkout P0 Path

1. Overview & Rationale

During heavy transaction surges, upstream Stripe Tax calculation RPCs periodically breach our standard 200ms checkout latency budget. To prevent hard cart abandonment, the billing-service intercepts breaches, applies a bounded local heuristic fallback calculation, and responds with HTTP 202 Accepted immediately to unblock customer checkout.

2. Data Flow & Queue Topology

The fallback path offloads accurate settlement calculation to an asynchronous worker queue:

Checkout Client → POST /v1/checkout/tax-quote
↳ Stripe timeout breached (>200ms threshold)
↳ Postgres Advisory Lock acquired on order key
↳ Dispatch message to SQS Topic: billing-tax-reconcile-p1
↳ Return HTTP 202 with synthetic tracking metadata
Background Worker ← Consumes SQS topic → Runs async Stripe Tax reconcile

3. Idempotency & Concurrency Control

To prevent double deductions and out-of-order race conditions when both the delayed Stripe response and the async reconcile event arrive concurrently:

  • Generate deterministic transaction token: tax_tx_{order_id}_{attempt}.
  • Protect database mutate operations using transient Postgres transaction advisory locks: pg_try_advisory_xact_lock(hashtext(order_id)).
  • Maintain an immutable journal of reconciliation state transitions in billing_reconciliation_audit.

4. Code & Implementation Baseline

src/handlers/tax-fallback.ts TypeScript 5.4 
// Fallback webhook ingestion & async dispatch
export async function handleTaxFallback(req: Request, res: Response) {
  const { orderId, currency, subtotalCents, address } = req.body;
  const syntheticTag = `synthetic_fallback_${Date.now()}`;
  
  await queue.publish("billing-tax-reconcile-p1", {
    orderId,
    syntheticTag,
    retryPolicy: { maxBackoffMs: 5000 }
  });

  return res.status(202).json({
    status: "accepted",
    tag: syntheticTag
  });
}

5. Error Handling & Dead-Letter Policy

Failed reconciliation consumer runs execute exponential backoff (initial 500ms, max multiplier 5000ms) capped at 3 discrete attempts. Exhausted executions transfer directly to Dead-Letter Queue:

arn:aws:sqs:us-east-1:182930491823:billing-tax-dlq Retention: 14d
