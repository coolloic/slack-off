# Slack Off（摸鱼）— 项目计划书 / 设计文档

- 日期：2026-11-06
- 状态：草案，待审批
- 形态：开源项目，第一版在开发者本机运行

---

## 1. 意图与背景

Slack Off 是给软件开发工程师用的本地平台：把一张 JIRA 票从 **Ready for Dev** 一路推进到 **Ready for Human Review**，中间的大部分工作交给多个 AI agent 完成，开发者只在少数关键节点"拍板"。

为什么做：
- 工程师日常大量时间花在"读票 → 理清需求 → 想方案 → 写代码 → 自测 → 写 PR 描述"这条固定链路上，其中多数步骤可以由 agent 完成。
- 开发者不需要一直盯着 agent，可以离开，在需要决策时被叫回（通过平台 UI，早期也可通过 Claude Code Remote Control）。
- 每个决策和 agent 之间的争论都留档，可审计、可追溯。

"Slack Off / 摸鱼"只是项目名。

## 2. 目标、非目标、反目标

### 目标
1. 自动发现分配给"我"的全部未完成 JIRA 票（不再只看 Ready for Dev；开发者逐票决定处理哪些）。（作者决定 2026-11-06：拉取分配给我的全部未完成票）
2. Agent 读取票的描述和评论，整理出结构化的完整需求和验收标准（AC），既用于 UI 展示，也作为后续 agent 的输入。
3. Agent 给出一个或多个有取舍的方案，列出优缺点，由开发者选择。
4. 选定后，设计 agent 写出详细设计文档（边界情况、错误处理、性能、安全、兼容性、测试策略等）；挑刺 agent 找漏洞；两者讨论后定稿。讨论全程记录，用于审计。
5. 开发 agent 在隔离的工作区迭代开发，状态同步回 UI 和 JIRA。
6. 开发者通过 UI 把票交给验收 agent。验收 agent **只能看到需求和 AC**，独立判断业务需求是否满足、边界是否覆盖，执行 e2e 测试，生成带截图的验收报告。
7. 开发者确认验收报告并在确认框中核对要执行的全部动作后，平台推送分支、每个受影响仓库开一个 PR（互相引用）；开启 JIRA 状态同步（`jira.syncStatus`）时，交付中再把 JIRA 标为 Ready for Human Review 并评论 PR 链接。
8. 两种 JIRA 接入方式：浏览器（默认）和 JIRA API。
9. 两种 agent 执行方式：Claude Code 订阅（默认）和 Claude API（可选），文档中清楚对比优缺点，由用户自选。

### 非目标（第一版不做）
- 多用户、团队共享部署、权限体系。第一版只在单个开发者本机运行。
- 替代人类代码评审。平台的终点是"可供人评审的 PR"，不是合并。
- 支持 JIRA 以外的工单系统（架构上留口子，但不实现）。
- 引入 LangChain / LangGraph（作者确认，2026-11-06）：它们通过 API key 调用模型，与默认的订阅模式不兼容；编排已由 SQLite 状态机 + 任务队列承担，引入后会形成两套状态机。API 模式成熟后可在阶段 4 之后重新评估。
- 自动合并 PR、自动部署。

### 反目标（即使能跑也算失败）
- Agent 在开发者不知情的情况下对外产生影响：未经确认就在 JIRA 发评论、改状态以外的字段、push 代码或开 PR。
- 验收 agent 读到了设计文档或开发过程，失去独立性（变成"自己验自己"）。
- 改动开发者正在使用的工作目录或主分支。
- 平台持有或要求用户输入 Claude 账号凭证或 JIRA 密码。
- 无声失败：agent 卡住、额度耗尽或出错时不通知开发者。
- 审计记录不完整或可被事后静默修改。

## 3. 约束

- **语言与运行时**：TypeScript；Node.js 26 LTS 直接运行 `.ts`（内置类型擦除），服务端不需要编译步骤。tsconfig 开启 `erasableSyntaxOnly`，禁用 enum、namespace、参数属性等需要转换的语法。
- **数据库**：Node 内置 `node:sqlite`，单文件数据库，存放在用户本地数据目录。
- **Claude 访问**：作者只有 Claude Code 订阅，没有 API key。订阅模式必须是一等公民、默认选项；API 模式为可选。
- **订阅模式的合规方式**：平台调起用户本机已安装且已登录的 `claude` CLI，不在平台内实现 Claude 登录，不读取或保存 Claude 凭证。
- **JIRA 浏览器模式**：通过 Claude Code 的 claude-in-chrome 能力，使用开发者自己浏览器里的登录状态访问 JIRA。
- **开源定位**：README 中把浏览器模式描述为"无需 API token，使用你自己的浏览器登录状态"，不使用"绕过 governance"一类的表述；并明确提醒使用者：把代码和工单内容发送给 AI 是否符合所在公司政策，由使用者自行判断。
- **本机优先**：服务端默认只监听 `127.0.0.1`。
- **手机远程访问（作者确认，2026-11-06）**：开发者外出时主要用手机完成拍板。通过 **Tailscale** 私有网络访问：在设置中开启"远程访问"后，服务端额外监听本机的 Tailscale 地址（绝不监听 0.0.0.0），Host / Origin 白名单加入该地址与 MagicDNS 名；所有非本机请求必须携带已配对设备的会话（设置页生成一次性配对链接 / 二维码，手机打开后获得长期 HttpOnly + SameSite=Strict 会话 cookie，库中只存哈希，可在设置中撤销）；本机请求免配对。服务端直接托管构建好的 UI。不使用公网暴露方案。

## 4. 已决定的技术选型

| 部分 | 选型 | 说明 |
|---|---|---|
| 仓库结构 | pnpm monorepo：`packages/server`、`packages/web`、`packages/shared` | `shared` 放共享类型和 schema |

| 单元测试 | `node:test` | |
| e2e / 截图 | Playwright | 用于平台自身的 e2e，也用于验收 agent 对目标项目做 e2e 和截图 |
| Git | 每张票一个 git worktree + 分支，命名如 `slackoff/PROJ-123-short-slug` | |

## 5. 票的生命周期

### 5.1 状态机（平台内部状态）

```
discovered（发现）
  → refining（整理需求中）
  → refined（需求已整理）
  → [可选] awaiting_ac_review（等待开发者审阅/编辑需求和 AC） ◀ 拍板点 0（默认跳过）
  → proposing（生成方案中）
  → awaiting_choice（等待开发者选方案）      ◀ 拍板点 1
  → designing（设计 + 辩论中）
      ├─ 辩论超 3 轮仍有阻塞分歧 → awaiting_debate_ruling（等待开发者裁决分歧） ◀ 拍板点 1.5
      │     ├─ 全部采纳设计方 → design_final
      │     ├─ 其他裁决 → designing（设计 agent 按裁决修改后再定稿，见 §9.3）
      │     └─ 改选方案 → awaiting_choice
  → design_final（设计定稿）
  → checking_snapshot（开发前复读 JIRA 快照；有变化时做偏移检查）
      ├─ 偏移需要已知晓（无出处 / 矛盾） → awaiting_snapshot_ack（等待开发者已知晓，须填说明） ◀ 拍板点（快照变化已知晓）
      │     ├─ 已知晓并开始开发 → developing
      │     └─ 从需求重新规划 → refining
  → developing（开发中；每个受影响仓库一个 worktree）
  → dev_done（开发完成，等待交给验收）       ◀ 拍板点 2：开发者点"交给验收"
      ├─ 要求修改（附说明） → developing（新一轮开发迭代）
      └─ 改选方案 → awaiting_choice
  → reviewing（独立验收中；交给验收前先复读 JIRA 快照并做偏移检查）
      ├─ 偏移需要已知晓 → awaiting_review_ack（等待开发者已知晓，须填说明） ◀ 拍板点（验收前快照变化已知晓）
      │     ├─ 已知晓并开始验收 → reviewing
      │     └─ 从需求重新规划 → refining
      ├─ 失败 → 回到 developing（自动修复循环，有上限 review.maxAttempts，默认 3）
      │     └─ 修复迭代完成 → reviewing（developing → reviewing，不经过 dev_done）
  → awaiting_confirmation（等待确认验收报告；通过、失败到上限以外的结论或 e2e 未执行都停在这里） ◀ 拍板点 3
      ├─ 驳回并附意见 → developing（代码需要修改；修复后直接回到验收，开始新一轮）
      ├─ 重新验收并附意见 → reviewing（验收 agent 判断有误；计入当前轮的上限）
      └─ 确认并交付 → delivering
  → delivering（交付执行中：快照复读 → push → 开 PR → PR 互相引用 → [可选] JIRA 状态 → [可选] JIRA 评论）
      └─ 开 PR 前复读快照发现需要已知晓的偏移 → awaiting_confirmation（重新查看后再确认）
  → pr_opened（所有受影响仓库的 PR 均已开）

pr_opened 只表示所有 PR 已开。JIRA 状态（Ready for Human Review）与 JIRA 评论两步在其后独立记录，
可单独重试；它们失败只记录，不改变平台状态。push / 开 PR 失败 → blocked（重试时已完成的步骤不重复）。

任意状态 → blocked（卡住，需要人介入；附原因）
任意状态 → abandoned（开发者放弃）
```

### 5.2 与 JIRA 状态的同步
- 进入 `developing` 时：**可选**把 JIRA 改为 In Progress（`jira.syncStatus`，默认关闭）。开启后每次写都需开发者在 UI 上明确确认（"Send to JIRA"，本机或已配对手机均可，审计记录来源设备）；票已是目标状态时跳过并说明；写失败只记录，不阻塞、不改变票的平台状态。（作者决定，阶段 2）
- 交付时：`jira.syncStatus` 开启时，把 JIRA 改为 Ready for Human Review（`jira.reviewStatus`，仓库规则 `jiraStatus.readyForReview` 可覆盖）并发表评论附 PR 链接，二者作为交付确认中逐条列出的步骤执行（只在开发者确认后发生；失败只记录、可单独重试，不改变平台状态）。（阶段 3）
- 每个项目的 JIRA 状态名不同，需要可配置的映射表（项目规则文件里配置，见 §9.5）。
- 所有对 JIRA 的写操作都写入审计日志。

### 5.3 每一步说明

1. **发现**：定时或手动触发，扫描分配给当前用户的全部未完成票（JQL `assignee = currentUser() AND statusCategory != Done ORDER BY updated DESC`，逐页读取，最多 `jira.discoverLimit` 张，默认 100，范围 1–500；超出上限或有页读不到时标记为"不完整"）。"Ready for Dev"状态名只作为票列表的默认 JIRA 状态筛选和高亮。一次**完整**的拉取中不再出现的已知票标记为"JIRA 中已不再打开"（只改这个标记并记审计，不改平台状态、需求和方案，也不自动放弃）；不完整或失败的拉取不改任何标记。（作者决定 2026-11-06：拉取分配给我的全部未完成票）发现之后**不会自动开始整理**，由开发者在列表里勾选要处理的票，以节省订阅额度；可在设置中打开"自动整理"（文档作者的决定）。

**全局配置与仓库映射**（文档作者的决定）：全局配置文件保存 JIRA 地址、接入方式、"Ready for Dev"等状态在全局使用的名称、执行器选择，以及 JIRA 项目 key 到本地仓库路径和基础分支的映射（例如 `PROJ → ~/work/proj，base: main`）。一个 JIRA 项目对应多个仓库时，由开发者在票详情页手动选择。仓库里的规则文件（§9.5）可以覆盖全局的状态名映射。
2. **整理需求**：读取标题、描述、评论、附件名、关联票，输出结构化需求：背景、功能需求列表、AC 列表（每条可验证）、不清楚或矛盾之处、引用的原文出处。
2a. **（可选）审阅需求和 AC**：全局默认**跳过**，整理完直接出方案。可以给单张票打开"出方案前需审阅"（在票列表或详情页切换），打开后票停在 `awaiting_ac_review`，开发者可以直接编辑需求和 AC，确认后再继续。每次编辑都生成新的需求版本并写入审计日志。后续各阶段都锁定某个需求版本；如果选完方案后需求又变了，平台提示开发者选择"从出方案重新开始"或"沿用当前方案继续"。

3. **出方案**：基于需求和目标仓库代码，给出 1～N 个方案。每个方案包含：思路、改动范围、优点、缺点、风险、预估复杂度。开发者在 UI 上选一个，可附备注。选择记录入库。
4. **设计 + 辩论**：设计 agent 写详细设计；挑刺 agent 指出漏洞；设计 agent 回应或修改；循环直到挑刺 agent 没有阻塞性问题，或达到轮数上限（见 §9.3）。每一轮的完整内容入库。

   设计文档和挑刺都必须**逐项覆盖**一份质量检查清单。清单中的每一项都要明确写"已考虑，结论是……"或"不适用，理由是……"，不能跳过：
   - **非功能性需求**：可读性、可维护性、可扩展性、可观测性（日志、指标、链路追踪、告警）、安全性（输入校验、鉴权、敏感数据、依赖风险）、可重用性、性能、可靠性和错误处理、向后兼容、可测试性
   - **设计原则**：SOLID、DRY、KISS、YAGNI、关注点分离，以及与仓库现有架构和约定是否一致
   - **边界与异常**：空值、极值、并发、超时、重试、部分失败

   清单默认内置，可在项目规则文件（§9.5）中增删。挑刺 agent 每条意见都要标注对应的清单项，以及"阻塞 / 非阻塞"。UI 的辩论记录页按清单项展示覆盖情况。
5. **开发**：开发 agent 在独立 worktree 中按定稿设计实现，写测试，小步 commit（commit 信息带票号）。每完成一轮更新 UI 进度。
6. **独立验收**：开发者在 UI 点"交给验收"。验收 agent 的上下文**只有**整理后的需求和 AC，以及代码快照和运行环境。它逐条对照 AC 判定通过或失败，执行 e2e，截图，生成报告。

   **验收的定位（作者确认）**：模拟最终用户，测试所有可能的使用流程，包括正常流程、异常流程和边界情况，确保所有功能和输出结果都正确。验收以黑盒为主：从用户能接触到的入口去操作，不以"读代码觉得没问题"作为通过依据。

   **不同类型项目的"最终用户入口"**（文档作者的决定）：在项目规则文件里声明入口类型和启动方式。
   - Web 应用：用 Playwright 驱动一个**独立的**浏览器（不使用开发者已登录的 Chrome），每个关键步骤截图。
   - 后端服务 / API：以调用方身份发真实请求，证据是请求和响应的记录。
   - 命令行工具：以用户身份执行命令，证据是命令和终端输出。
   - 库：写一个最小的调用示例来使用它，证据是示例代码和运行输出。

   第 3 期优先实现 Web 应用和 API，命令行工具和库放到第 4 期。报告中每条 AC 都要列出：测试的流程步骤、预期结果、实际结果、证据（截图或日志），以及通过 / 失败。验收 agent 自己设计测试流程，至少覆盖每条 AC 的正常路径、一条以上的异常路径，以及相关的边界值。
7. **失败回流**：失败的 AC 条目和证据交回开发 agent 修复，然后重新验收。自动循环上限为 `review.maxAttempts`（默认 3，可配置 1–5，按验收轮次计数），超过则进入 `blocked` 并通知开发者。
8. **确认与交付**：开发者在 UI 上查看报告并确认 → 平台 push 分支 → 开 PR（描述包含需求摘要、所选方案、验收报告摘要，并写明截图与证据在 Slack Off 中；不含截图链接、不嵌入或提交任何截图——JIRA 与应用数据不外泄到 GitHub，裁决 2026-11-07）→ 更新 JIRA（`jira.syncStatus` 开启时，经确认）。

## 6. Agent 角色与上下文隔离

| 角色 | 能看到 | 产出 |
|---|---|---|
| 需求整理 agent | JIRA 票内容 | 结构化需求 + AC + 疑问点 |
| 方案 agent | 需求 + 目标仓库代码 | 方案列表（含优缺点） |
| 设计 agent | 需求 + 选定方案 + 开发者备注 + 代码 | 详细设计文档 |
| 挑刺 agent | 需求 + 设计文档 + 代码 | 漏洞清单（区分阻塞 / 非阻塞） |
| 开发 agent | 需求 + 定稿设计 + 代码 + 验收失败反馈 | 代码、测试、commit |
| 验收 agent | **仅**需求 + AC + 代码 + 可运行环境 | 验收报告 + 截图 |

隔离原则：每个角色都是**全新的会话**，上下文由平台显式组装，不继承上一个 agent 的会话。验收 agent 的隔离是硬性要求，必须有测试保证它拿不到设计文档和辩论记录。

验收 agent 的隔离做到文件系统层面（文档作者的决定）：
- 不在开发 worktree 里运行，而是用 `git archive` 导出一份**不带 git 历史**的代码快照，在独立目录中运行。
- 使用独立的 Claude 配置目录（`CLAUDE_CONFIG_DIR`），看不到其他 agent 的会话记录。
- 不允许访问平台的数据目录和数据库。
- 开发 agent 写的测试和代码注释会留在快照里，这可以接受：验收 agent 必须自己写 e2e，不能只跑已有测试就算通过。
- 隔离测试检查：验收 agent 的工作目录和配置目录中不存在设计文档、辩论记录、数据库文件、`.git` 目录。
- 验收用例、它启动的浏览器与目标应用在 macOS `sandbox-exec` 中运行（平台的 `playwright` shim），拒绝读取凭证与平台数据目录、拒绝连接 Slack Off 自己的端口；`claude` 进程本身不在 OS 沙箱中。（裁决 R-LOCAL / T1-1，阶段 3）

### 7.1 Executor 抽象
上层流程只依赖一个统一接口，大致是：给定角色、组装好的上下文、工作目录、允许使用的工具，返回结构化结果和过程事件流（用于 SSE 展示和审计）。

- **ClaudeCodeExecutor（订阅模式）**：以无界面模式调起 `claude`（结构化 JSON 流输出），按角色限制可用工具和权限。需要浏览器操作时启用 claude-in-chrome。
- **ClaudeApiExecutor（API 模式）**：以用户提供的 API key 认证运行同一个 Claude Code CLI（同一组沙箱参数），实现同一接口（裁决 B-1，2026-11-09）。

两种模式对比（写进 README，供用户自选）：

| | 订阅模式（默认） | API 模式 |
|---|---|---|
| 需要什么 | Claude Code 订阅 + 本机已登录的 `claude` | Anthropic API key |
| 费用 | 包含在订阅里 | 按 token 计费 |
| 上手难度 | 低，能力现成（浏览器、改代码、跑命令） | 较高，浏览器等能力需另外接入 |
| 并发与额度 | 受订阅额度限制，多 agent 并发容易撞上限 | 主要受账户速率限制和预算约束 |
| 控制粒度 | 较粗，通过 CLI 参数控制 | 细，可精确控制工具、模型、上下文 |
| 适合 | 个人开发者、试用 | 重度自动化、团队统一付费 |

### 7.2 TicketSource 抽象
统一接口：列出待办票、读取票详情（含评论）、更新状态、发表评论。浏览器模式由一个专门的 agent 通过 claude-in-chrome 操作 JIRA 页面，把结果按 schema 返回；API 模式直接调 REST。

### 7.3 拍板与通知
- **主入口是 UI**：选方案、交给验收、确认验收报告、处理 blocked。
- **早期过渡**：UI 还没完成的拍板点，允许通过 Claude Code Remote Control 处理。具体做法留给实现者，但阶段 1 结束时 UI 必须覆盖拍板点 1。
- 等待开发者时，UI 中显著提示；可选启用系统通知。

## 8. 数据模型（概要；完整字段见 `docs/ba/05-er.mmd`）

- `ticket`：JIRA key、标题、原始内容快照、平台状态、所属仓库、分支、worktree 路径
- `requirement`：所属票、版本、结构化需求（JSON）、AC 列表、疑问点
- `solution`：所属票、序号、内容、优缺点、风险、复杂度
- `choice`：所属票、选中的方案、开发者备注、时间
- `design_doc`：所属票、版本、内容、是否定稿
- `debate_round`：所属票、轮次、角色、内容、阻塞问题列表
- `debate_ruling`：拍板点 1.5 的逐条裁决（分歧、采纳设计方 / 采纳挑刺方 / 自定义、备注）
- `dev_iteration`：所属票、轮次、commit 列表、摘要、触发原因（初次 / 验收失败）
- 验收与交付（迁移 9，阶段 3）：`review_series`（验收轮次：交给验收 / 驳回 / 上限后重试各开始一轮）、`review_report`（所属轮次、第几次、结论、完整报告 JSON、开发者说明、所依据的 JIRA 快照）、`review_evidence`（报告的截图 / 证据文件，键 `<acId>/<n>`）、`review_decision`（拍板点 3 的驳回 / 重新验收 / 确认）、`acceptance_run`（验收进程登记，重启恢复时清理）、`delivery`（一次确认并交付：计划哈希、确认人）、`delivery_step`（交付的逐条步骤及状态、结果）、`jira_comment`（澄清 / 交付评论及确认、发送状态）
- `agent_run`：角色、执行器类型、skill 版本、提示词版本、开始结束时间、消耗（token 或额度估算）、结果状态
- `audit_event`：时间、操作者（开发者 / 具体 agent / 系统）、事件类型、对象、内容。**只增不改**；每条记录保存上一条的哈希，形成哈希链，便于发现事后篡改。
- `prompt_version`：每个角色的用户提示词版本（§9.6）
- `preference`：开发者的选择偏好记录（见 §9.4）

截图等大文件存本地数据目录，库中只存路径。

原始票据快照、AC 出处、偏移检查的实体（`ticket_snapshot`、`snapshot_comment`、`snapshot_attachment`、`ac_trace`、`drift_check`）见 §9.9。

## 9. 附加功能（已确认全部保留）

### 9.1 成本与额度面板
展示每张票、每个 agent 运行的消耗：API 模式显示 token 和费用；订阅模式显示运行次数、时长，以及从 CLI 输出中能拿到的用量信息。可设阈值，快到上限时自动暂停新任务并通知。

### 9.2 需求不清自动检测
需求整理时，若 AC 缺失、相互矛盾或无法验证，标记为"需求不清"，并起草一条向 PM 或报告人提问的 JIRA 评论。**开发者确认后才发送。**票可停在 `refined` 等待澄清。

### 9.3 辩论轮数上限
设计和挑刺默认最多 3 轮（可配置）。到上限仍有阻塞问题时，票进入 `awaiting_debate_ruling`，平台生成分歧摘要（双方观点、各自理由）。开发者对每条分歧选择"采纳设计方 / 采纳挑刺方 / 填写自己的意见"：全部"采纳设计方"时直接定稿；否则票回到 `designing`，由设计 agent 按裁决修改设计（对每条采纳挑刺方或自填意见的分歧逐条回应），然后定稿，不再进入新一轮挑刺；如果认为方案本身有问题，可选"改选方案"回到 `awaiting_choice`。裁决结果入审计日志。

### 9.4 记住选择偏好
记录开发者每次选方案的特征（例如偏简单 / 偏可扩展、是否引入新依赖），形成偏好摘要，在下次生成方案时作为参考提供给方案 agent。开发者可在 UI 查看、编辑、清空。

### 9.5 项目规则文件
每个目标仓库可以放一份规则文件（例如 `.slackoff/rules.md` 加一份配置文件），内容包括：代码规范、禁止改动的路径、测试和启动命令、e2e 怎么跑、JIRA 状态名映射、分支命名规则。所有 agent 必须遵守；违反禁止路径的改动在 commit 前被平台拦截。

### 9.6 每个 agent 的系统提示词配置
- UI 设置页提供一个配置窗口：每个角色（需求整理、方案、设计、挑刺、开发、验收、JIRA 浏览器）各有一个可编辑的提示词，用来调整输出质量和风格，例如"方案最多 3 个""用中文输出""偏好函数式风格"。
- 分两层：全局配置，加上仓库级覆盖（仓库规则文件中可以为某个角色追加或替换提示词）。
- 用户提示词**追加**在平台内置提示词之后，不能覆盖平台内置的硬性约束：输出必须符合 schema、验收 agent 的隔离、禁止路径、对外操作前必须确认。
- 提示词有版本记录。每次 agent 运行时实际使用的提示词版本记入 `agent_run`，便于审计和对比效果。
- 每个角色提供"恢复默认"，以及用一张样例票"试运行"的入口（阶段 4 实现，文档作者的决定）。
- 订阅模式下通过 CLI 的追加系统提示词参数传入；API 模式下直接拼进 system prompt。
- 用户提示词叠加在该角色的 skill（§9.7）之上。

### 9.7 Agent 角色以 Claude Code skill 形式发布（作者确认，2026-11-06）
- 每个角色是一个独立的 Claude Code skill，放在仓库 `skills/` 下：`jira-browser`、`refine-ticket`、`propose-solutions`、`design-solution`、`critique-design`、`implement-ticket`、`acceptance-review`，以及只在开发者拍板后由平台调起的写操作 skill `jira-update`、`jira-comment`（每次只做一件指定的写操作；`jira-comment` 只在该票自己的页面输入平台给定的那段评论文本）。
- 每个 skill 包含：角色说明、该角色的质量检查清单（设计和挑刺使用 §5.3 的清单）、输入约定、输出 JSON schema 说明、禁止事项。
- **平台使用方式**：执行器调起 `claude` 时加载对应 skill，再把平台组装好的上下文作为输入。平台内置的硬性约束（schema、隔离、禁止路径、对外操作需确认）由平台自身保证，不依赖 skill 内容。
- **独立使用方式**：开发者不装平台，也可以在自己的 Claude Code 里安装这些 skill，单独执行某一步（例如对一张票执行需求整理，或对一份设计执行挑刺）。README 单独介绍这种用法。
- skill 随平台版本一起发布；`agent_run` 记录本次使用的 skill 版本（取 git 提交号或 skill 文件哈希）。

### 9.8 运行追踪（可选，阶段 4）
- 平台以 OpenTelemetry 记录每次 agent 运行（角色、耗时、工具调用、结果状态、消耗）。
- 默认**不导出**到任何外部服务；配置导出地址后，可接入 LangSmith、可自部署的 Langfuse 或其他兼容后端。README 提醒：导出会把票内容和代码片段发送给该服务。

### 9.9 原始票据快照与 AC 偏移检查（作者提出，2026-11-06）
目的：保留 JIRA 原始内容作为审计依据，并能验证整理或编辑后的 AC 有没有偏离原始需求。
- **快照只增不改**：每次读取 JIRA 生成快照，包括标题、描述、全部评论（含评论 ID、作者、时间）、附件和内嵌截图。图片下载到数据目录，记录 sha256。内容哈希相同则不新建；不同则新建，并链接上一版、记录变化摘要。快照写入后不允许修改，写入事件进审计日志。
- **重新读取时机**（文档作者的决定）：整理需求时、进入开发前、开 PR 前。发现 JIRA 内容变化时通知开发者，并触发偏移检查。
- **AC 出处**：需求整理 agent 必须为每条 AC 给出来源（快照中的描述段落、评论 ID 或附件），并附原文片段；开发者手动新增的 AC，来源记为"开发者新增"且必须填写理由。
- **偏移检查**：以该票**最初的快照**为基准，逐条判定 AC 为"有出处 / 部分有出处 / 无出处 / 与原文矛盾"。触发时机：AC 被编辑后、快照变化后、交给验收前。
- **处理方式**（文档作者的决定）：只警告、不阻塞；存在"无出处"或"矛盾"时，开发者必须点"已知晓"才能继续，该操作写入审计。
- **AC 对照**（作者提出）：偏移检查同时输出一张对照矩阵。基准项包括：(a) 最初整理出的 AC（需求 v1，或开发者指定的版本）；(b) 从 JIRA 评论中提炼出的**讨论结论**（D-n，每条附来源评论 ID，由需求整理 agent 产出并随需求保存）。每个基准项标注被当前哪些 AC 覆盖：完全覆盖 / 部分覆盖（附差异说明）/ 丢失。当前 AC 中找不到对应基准项的标为"新增"，再按出处区分。对照结果存于 `drift_check.result_json`。
- UI：票详情页可以查看原始快照（含截图）、各版本之间的差异、每条 AC 的出处链接，以及 AC 对照矩阵和偏移检查记录（见 `docs/ba/functional-spec.md` §6）。
- 偏移检查由 `refine-ticket` skill 的"核对模式"执行，不新增角色。
- 分期：快照、AC 出处、AC 编辑后的偏移检查放在阶段 1；快照变化和交给验收前的检查随阶段 2、3 实现。

## 11. 主要风险与需要尽早验证的点

1. **claude-in-chrome 在无界面 CLI 模式下是否可用、是否稳定**：这是浏览器模式的基础，阶段 1 第一件事就是做一个技术验证（throwaway），不行就调整方案（例如让浏览器 agent 用交互式会话运行）。
2. **Remote Control 能否用于平台调起的会话**：同样在阶段 1 早期验证；不行就加快 UI 拍板点的开发。
3. **订阅额度**：多 agent 并发可能很快耗尽额度。默认并发数为 1，可配置。
4. **JIRA 页面结构差异**（Cloud vs Data Center、自定义字段）：浏览器 agent 用"看页面理解内容"的方式读取，输出必须通过 schema 校验，失败则重试或标记 blocked。
5. **目标项目的 e2e 环境**：验收 agent 需要知道怎么启动目标应用，依赖项目规则文件里的启动和测试命令；没有配置时，验收报告要明确标注"未执行 e2e"，不能假装通过。
