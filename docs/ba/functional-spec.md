# Slack Off · 功能说明书（供 Google Stitch 出 UI 设计）

- 版本：v0.1 草稿（2026-11-06）
- 依据：`docs/superpowers/specs/2026-11-06-slack-off-design.md`，以及画板 BA-01 ~ BA-05
- 用法：每个页面一节，可以把"全局设计要求"加上某一节直接交给 Stitch 生成该页面。

---

## 0. 全局设计要求（每次交给 Stitch 时都附上）

- **产品**：Slack Off 是开发者本机运行的 Web 应用。多个 AI agent 负责把 JIRA 票从 Ready for Dev 推进到 Ready for Human Review，开发者只在几个"拍板点"做决定。
- **用户**：软件开发工程师。习惯 IDE、GitHub、JIRA，偏好信息密度高、键盘友好的界面。
- **风格**：开发者工具风格，参考 Linear / GitHub 的克制感。浅色、深色两套主题；等宽字体用于票号、分支名、代码和 JSON。不要营销式大图，也不要插画。
- **界面语言**（作者确认，2026-11-06）：界面文字以**英文**为主，所有文案集中管理，预留中文（zh-CN）切换。交给 Stitch 的提示词使用英文，生成的页面文案为英文。
- **布局**（作者 2026-11-06 更新）：**移动优先、响应式**。所有页面在 375px 宽的手机上可用、无横向滚动；桌面（≥1280px）为左侧窄导航 + 主内容区（可分栏）。窄屏：侧栏收成菜单；右侧决策卡移到内容顶部或底部固定按钮；表格变卡片列表；AC 对照每个基准项一张卡片，对应的当前 AC 在卡片内；方案卡片纵向堆叠；页签可横向滚动。手机上优先保证"需要你决定"列表与各拍板卡片顺手（开发者常在手机上远程拍板）。
- **状态色**（全局统一）：
  - 进行中（agent 在跑）：蓝
  - 等待开发者拍板：橙（最醒目，带脉冲点）
  - 完成 / 通过：绿
  - blocked / 失败 / 矛盾：红
  - 放弃 / 未开始：灰
- **拍板点**的视觉统一：橙色边框卡片 + 标题"需要你决定" + 主按钮。所有对外写操作（改 JIRA、发评论、push、开 PR）的按钮旁都注明"将会：……"。
- **每个页面都要画出四种状态**：加载中（骨架屏）、空、出错（带重试）、正常。等待拍板的页面再加一种"等待拍板"状态。
- **实时性**：agent 运行中的区域显示实时活动流（类似终端日志，可折叠）。

## 1. 全局框架

**目的**：在任何页面都能看到"哪里需要我"和"系统是否正常"。

**展示**
- 左侧导航：票、审计日志、成本与额度、设置。
- 顶栏：
  - "待你拍板"计数徽标，点击展开列表（票号 + 拍板点类型 + 等待时长）。
  - 执行器状态：订阅模式或 API 模式，`claude` CLI 是否可用、是否已登录。
  - JIRA 连接状态：浏览器模式下 Chrome 扩展是否连接、JIRA 是否已登录。
  - 当前并发：运行中的 agent 数 / 上限。
- 全局横幅（出现时置顶）：例如"JIRA 登录已过期，请在 Chrome 中登录后重试"、"额度即将用尽，新任务已暂停"。

**操作**：点击徽标跳到对应票的拍板区域；横幅上提供"重试"按钮。

**状态**：执行器不可用时，顶栏执行器图标变红，悬停显示原因（未安装 / 未登录）。

---

## 2. 票列表 / 看板

**目的**：一眼看到所有票走到哪一步，以及哪些在等我。

**展示**
- 两种视图可切换：
  - 列表：表格。
  - 看板：按阶段分列，依次为 发现 / 整理需求 / 方案 / 设计 / 开发 / 验收 / 已开 PR / blocked。
- 每张票：票号（等宽）、标题、平台状态徽标（用状态色）、JIRA 状态（等于设置中"Ready for Dev"状态名时高亮；完整拉取中不再出现的票显示"No longer open in JIRA"徽标）、所属仓库、最近更新时间、当前运行的 agent（如有，带转圈）、"出方案前审阅"开关、偏移警告图标（存在"丢失 / 矛盾"时显示红色）。
- 顶部：
  - "拉取新票"按钮，显示上次拉取时间；拉取分配给我的全部未完成票（作者决定 2026-11-06：拉取分配给我的全部未完成票），结束后显示"Found N new · M open in total"；
  - 上次拉取不完整时（达到上限或有页读不到）显示"Showing X of Y open tickets — raise the limit in Settings"，链接到设置；
  - 筛选：JIRA 状态（默认为设置中的"Ready for Dev"状态名；另有"All open"、列表中出现的每个 JIRA 状态，以及"Closed/reassigned"，只显示已不再打开的票；"All open"不含它们）、平台状态、仓库、只看待我拍板；
  - 搜索框。

**操作**
- 拉取新票。
- 勾选一张或多张"已发现"的票 → "开始整理"。
- 切换单票"出方案前审阅"。
- blocked 的票：查看原因，选择"重试"或"放弃"。
- 点击票进入详情。

**状态**
- 空：说明"还没有票，拉取分配给你的全部未完成票"，附"拉取新票"按钮。
- 拉取中：顶部进度条 + 活动流。
- 出错：例如"JIRA 登录过期"。

---

## 3. 票详情（框架）

**目的**：一张票的全部信息和全部拍板点都在这里。

**展示**
- 头部：票号、标题、JIRA 链接、平台状态、分支名（等宽，可复制）、worktree 路径。
- 进度条：沿着状态机，从发现一直到已开 PR；已完成的节点为绿色，当前节点高亮，拍板点为橙色。
- 右侧"需要你决定"卡片：只在等待拍板时出现，内容随拍板点变化。
- 页签：
  - 原始快照
  - 需求与 AC
  - AC 对照
  - 方案
  - 设计与辩论
  - 开发
  - 验收
  - 审计

**操作**：放弃这张票（二次确认）；重新整理需求。

---

## 4. 页签：原始快照

**目的**：保留 JIRA 原文，作为审计依据和 AC 的出处。

**展示**
- 快照版本时间线：v1、v2……每个版本显示抓取时间、JIRA 更新时间，以及"相对上一版的变化摘要"。
- 选中版本的内容：
  - 描述（保留格式）；
  - 评论列表：作者、时间、评论 ID；
  - 附件和内嵌截图：缩略图网格，点击放大，显示文件名和 sha256 前 8 位。
- "对比两个版本"：左右并排，增删高亮。
- 只读标识："快照写入后不可修改"。

**操作**：选择版本、对比版本、在 JIRA 中打开。没有编辑操作。

**状态**：JIRA 内容变化后，顶部提示"检测到 JIRA 已更新（v3），已触发 AC 偏移检查"。

---

## 5. 页签：需求与 AC（含拍板点 0）

**目的**：查看并（在需要时）编辑整理出的需求和 AC，每条 AC 都能追溯出处。

**展示**
- 需求版本选择：v1（agent 整理）、v2（开发者编辑）……
- 背景说明。
- 功能需求列表。
- AC 列表，每条显示：
  - 编号（AC-n）和文字；
  - 是否可验证；
  - **出处标签**：描述 / 评论 #ID / 附件 / 开发者新增。悬停显示原文片段，点击跳到原始快照里的对应位置。
- 讨论结论列表（D-n）：从 JIRA 评论中提炼出的结论，每条附来源评论。
- 需求不清区块（有疑问点时出现）：疑问点，以及给 PM 的评论草稿（只读，标注"阶段 3 才能发送"，阶段 3 起变为"确认后发送"）。

**操作**（仅在拍板点 0，即该票开启了审阅时可用）
- 增、删、改 AC。新增时必须选出处，或选"开发者新增"并填写理由。
- "确认需求" → 进入出方案。
- 保存时自动触发 AC 偏移检查，结果显示在"AC 对照"页签。

**状态**
- 未开启审阅：只读，右上角提示"本票默认跳过审阅"，可一键开启。
- 整理中：骨架屏 + agent 活动流。
- 输出格式错误被重试：活动流中显示"格式不符，重试 1/1"。

---

## 6. 页签：AC 对照（新增，作者提出）

**目的**：检查当前 AC 是否**完全覆盖**原始 AC 和讨论结论，并发现偏移。

**展示**
- 顶部摘要：基准 AC 12 条：完全覆盖 10 / 部分覆盖 1 / 丢失 1；讨论结论 4 条：覆盖 4；新增 AC 2 条（其中无出处 1）；矛盾 0。
- 基准选择："需求 v1（最初整理）"，或指定某个需求版本。
- **对照矩阵**（核心视图）：左右两栏，**按行对齐**表示覆盖关系（作者确认，2026-11-06，取代连线方案）。
  - 左栏是基准项：基准 AC（AC-n@v1），加上讨论结论（D-n，附来源评论）。
  - 右栏是当前版本 AC。
  - 同一行左右对应表示覆盖关系，每个基准项有状态徽标：完全覆盖（绿）、部分覆盖（黄，悬停看差异说明）、丢失（红）。
  - 右栏中没有连到任何基准项的 AC 标为"新增"，再按出处细分为：有出处（灰）、开发者新增 + 理由（蓝）、无出处（红）。
  - 任何与原文矛盾的项标红色"矛盾"，展开后并排显示原文片段与 AC 文字。
- 文字差异视图：可切到逐条 diff（旧 AC 文字 vs 新 AC 文字）。
- 检查记录：每次偏移检查的触发原因（AC 被编辑 / JIRA 更新 / 交给验收前）、时间、结果、是否已知晓。

**操作**
- "重新检查"。
- 存在丢失 / 无出处 / 矛盾时，显示橙色"需要你决定"卡片，可选：
  - "已知晓并继续"：必须填写说明，写入审计；
  - "回去修改 AC"。
- 点击任一项，跳到原始快照或需求页签的对应位置。

**状态**：全部覆盖且无新增无出处 → 绿色"完全覆盖"；检查进行中 → 骨架屏。

---

## 7. 页签：方案（拍板点 1）

**目的**：比较方案，选一个。

**展示**
- 方案卡片横向并排（1~5 个），每张：标题、思路摘要、改动范围（文件 / 模块列表）、优点、缺点、风险、复杂度（S / M / L 徽标）。
- "按维度对比"切换：表格视图，行 = 维度，列 = 方案。
- 选择偏好提示（若有）："你过去倾向于更简单、少依赖的方案"。
- 方案生成依据：需求 v?（版本锁定标识）。

**操作**：选择一个方案并填写备注（可选）→ "确认选择"；"重新生成方案"；"重新整理需求"。

**状态**：生成中（活动流）；等待选择（橙色卡片）。

---

## 8. 页签：设计与辩论（拍板点 1.5）

**目的**：查看设计文档、两个 agent 的辩论过程，必要时裁决分歧。

**展示**
- 设计文档（Markdown 渲染），版本切换 v1 / v2 / v3，带版本间 diff。
- **质量清单覆盖面板**：
  - 非功能性需求：可读性、可维护性、可扩展性、可观测性、安全性、可重用性、性能、可靠性、兼容性、可测试性；
  - 设计原则：SOLID、DRY、KISS、YAGNI、关注点分离、与现有架构一致；
  - 边界与异常。
  - 每项显示结论（已考虑 / 不适用 + 理由）和挑刺意见数。
- **辩论时间线**：按轮次排列。每轮包含挑刺 agent 的意见列表（每条标注清单项、阻塞 / 非阻塞）和设计 agent 的回应（接受并修改 / 反驳 + 理由）。
- 轮数指示：第 2 / 3 轮。

**操作**
- 拍板点 1.5（辩论超过 3 轮仍有阻塞分歧时）：分歧摘要逐条列出，双方观点并排。每条选"采纳设计方 / 采纳挑刺方 / 写我的意见"，全部处理后点"定稿"。或者点"改选方案"。
- 导出设计文档。

**状态**：辩论进行中（实时活动流）；已定稿（绿色标识 + 定稿时间）。

---

## 9. 页签：开发（拍板点 2）

**目的**：看开发进度，决定何时交给验收。

**展示**
- 分支名、worktree 路径、JIRA 已改为 In Progress 的时间。
- 开发轮次列表：触发原因（初次 / 验收失败 / 驳回）、commit 列表（hash、信息）、变更文件统计、测试结果。
- 实时活动流。
- 违反项目规则文件的拦截记录（如有）。

**操作**
- 拍板点 2："交给验收"（橙色卡片，注明"将会：导出无历史代码快照，交给独立验收 agent"）。
- 打开 diff（在本地编辑器或页面内）。

---

## 10. 页签：验收（拍板点 3）

**目的**：查看独立验收结果，决定开 PR、驳回或重新验收。

**展示**
- 结论横幅：通过 / 失败；第 n 次（≤3），附上限说明。
- 隔离说明："验收 agent 只看到需求与 AC、无历史代码快照"。
- 逐条 AC 结果表：AC 编号与文字 → 测试流程步骤 → 预期 → 实际 → 证据（截图缩略图 / 请求响应日志 / 命令输出）→ 通过 / 失败。
- 覆盖说明：每条 AC 测了正常 / 异常 / 边界中的哪些。
- 截图画廊：按 AC 分组，点击放大。
- 未执行 e2e 的情况要醒目标注，例如"项目规则未配置启动方式，未执行 e2e"。

**操作**（拍板点 3）
- "确认并交付"：注明"将会：先列出确切的动作清单再发送任何东西"；确认框逐条列出动作（重读 JIRA、push 分支、每仓库开 PR、互相引用；开启 JIRA 状态同步时还有：在交付中把 JIRA 改为 Ready for Human Review、评论 PR 链接）与 PR 描述全文，开发者确认后才执行。
- "驳回并附意见"：回到开发。
- "重新验收并附意见"：认为验收判断有误时使用，计入次数。

**状态**：验收中（活动流）；已开 PR（显示 PR 链接、JIRA 新状态）。

---

## 11. 审计日志

**目的**：完整、可验证的操作记录。

**展示**
- 顶部：哈希链校验结果（"完整"，绿；或"第 N 条起被篡改"，红）。
- 事件表：时间、操作者（开发者 / 系统 / agent:角色）、事件类型、票号、摘要；展开看完整内容（JSON）与哈希。
- 筛选：票号、操作者、事件类型、时间范围。

**操作**：重新校验；导出（JSON）。

---

## 12. 成本与额度

**目的**：知道花了多少，避免撞上限。

**展示**
- 按模式显示：
  - API 模式：token 与费用；
  - 订阅模式：运行次数、时长、可获取的用量。
- 按票、按角色、按天的统计图。
- 暂停阈值与当前进度条。

**操作**：设置阈值；手动暂停 / 恢复任务队列。

---

## 13. 设置

**分区**
1. **执行器**：订阅模式 / API 模式（单选，附两种模式的对比说明）；`claude` 路径；并发上限。
2. **JIRA**：地址、接入方式（浏览器 / API）、"Ready for Dev"等状态名映射（票列表默认筛选和高亮，不限制拉取）、每次拉取的最多票数（1–500，默认 100）、拉取 JQL 预览。
3. **仓库映射**：JIRA 项目 key → 本地仓库路径 + 基础分支（表格，可增删）。
4. **Agent 提示词**：
   - 角色列表：需求整理、方案、设计、挑刺、开发、验收、JIRA 浏览器、JIRA 更新；
   - 每个角色：只读显示对应 skill 名称和版本；
   - 可编辑的"补充提示词"文本框；
   - 版本历史（可查看、对比）；
   - "恢复默认"；
   - "用样例票试运行"（阶段 4 才可用，此前置灰）。
5. **流程**：自动整理开关、默认是否审阅 AC、辩论轮数上限、验收重试上限。
6. **运行追踪**（阶段 4）：OpenTelemetry 导出地址；警告"导出会把票内容和代码片段发送给该服务"。

**状态**：保存成功提示；校验错误逐字段显示。

## 交给 Stitch 的顺序（建议）

1. 全局框架 + 票列表（确定整体视觉）
2. 票详情框架 + AC 对照（最有特色、最复杂的视图）
3. 需求与 AC、原始快照
4. 方案、设计与辩论
5. 开发、验收
6. 审计、成本、设置
